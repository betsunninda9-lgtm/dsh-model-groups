# 开发与维护指南

日常安装和使用见 [README](../README.md)。

## 0.3.12-beta.3：按代码判定跨版本兼容

安装包不再声明 `engines.dsh` 或 DSH peer dependency 版本范围，保留 Node.js >=22；避免预发布 DSH 版本在读取程序之前被安装器阻断。原始 manifest 的 `version` 继续描述配方来源，不作为宿主或子包的准入值。

维护器识别正确的 DSH 及目标程序包身份，再按实际代码和所需关键结构规划补丁。DSH 版本、子包版本及其预发布或构建标签只记入诊断；版本号不同本身不会停止操作。仍在关键结构缺失、位置歧义、改动冲突或文件/事务条件不满足时停止多密钥维护，不影响独立的分组与折叠。不能把局部变换通过等同于任意版本的完整语义兼容。

公开兼容快照继续使用 `schema: 1` 和可空的 `supportedDsh` 字段以兼容旧客户端；新快照为 `supportedDsh: null`、`compatibilityPolicy: 'code'`，`hostVersion` 与各项 `installedVersion` 均来自实际安装元数据。`host_version` / `package_version` 旧诊断码只用于读取历史报告；当前身份错误使用 `host_identity` / `package_identity`，不会把版本差异误报为冲突。维护协议仍为 2，同协议的网页和后端无需插件版本号完全一致；协议不兼容时才要求刷新网页。

跨版本验收应分别覆盖：只改版本与预发布标签但程序不变、子包独立版本、程序的兼容格式/字段变化，以及关键结构真正不兼容。前几类应能继续计划、应用和还原，后一类应保留现场并指出文件原因；不自动降级，也不添加按版本登记或新的用户确认步骤。

维护票据只绑定维护协议、实际程序及目标配方哈希、操作权限等执行条件，不把版本标签纳入失效条件；只改元数据后刷新仍可沿用票据。已知旧补丁即使缺少当前基准的哈希映射，也会从精确配方确定的原版尝试新版正向变换；不重新猜测代码归属，避免把宿主原生已有的相似代码当成插件代码撤回。升级不适配时仍可按原精确配方还原。

## 按需启用与自动维护偏好

首次安装只提供折叠，不自动计划或写入多密钥补丁。首次手动启用成功后默认打开“自动维护多密钥补丁”；关闭自动维护保留当前补丁，后续宿主覆盖后手动恢复。主动关闭多密钥同时停止自动维护。偏好持久化于插件自己的安装指纹目录，不修改供应商配置或聊天。

已有安装仅依据本插件的旧备份/关闭标记等明确证据迁移，避免把新装用户当成旧用户。启动及空闲重试均先检查偏好；普通状态查询不安装补丁。设置页开关只保存本地偏好，不调用模型 API。

## 0.3.12：维护限制与兼容范围调整

启用、更新及自动恢复只为后续引擎启动准备磁盘补丁，不因当前对话正在生成而禁用。关闭、卸载仍单独检查运行中的任务；使用同一安装目录的其他引擎、文件冲突和并发维护锁仍会阻止写入。启用请求只检查与应用补丁相关的状态变化，卸载权限或回合状态变化不再导致请求失效。修复不会自动重启引擎、刷新网页或宣称已加载新模块；尚未加载的动态模块可能读取新文件，需按重启提示完成切换。

恢复流程等待 timer 服务就绪后启动，避免启动顺序使重试任务未注册；自动补回磁盘代码不依赖可选的 agents 服务。重试异常会结束等待并报告失败；不能确认进程状态与发现其他引擎分别提示。

词法定位依次收集 8、6、4 个 token 的双侧上下文候选，允许较远处无关标识符变化。所有窗口必须指向同一个位置；替换本体、换行约束及精确还原要求保持不变，不重新打印或覆盖宿主其他代码。该机制可扩大文本变化兼容范围，仍不能自动理解任意接口重构。

## 0.3.11-beta.2：启动恢复与片段兼容（历史行为）

0.3.11-beta.2 默认在插件启动时检查并自动补回兼容的多密钥补丁；npm `latest` 仍为 0.3.10，需明确安装此测试版。自动恢复尊重当前安装指纹目录下的 `restore-pending.json`：用户主动关闭后保持关闭，设置页点击 **启用多密钥**可显式恢复。任务运行或其他引擎等限制导致恢复暂缓时，插件在生命周期内每 5 秒检查活动状态，空闲后自动重试；恢复完成、明确关闭或失败后停止。网页在暂缓期间自动刷新状态，显示恢复结果和必要的重启提示。

整文件哈希用于已知版本识别、完整性与事务校验，但不再作为未知构建拒绝的唯一依据。DSH `0.2.2-rc.1` 范围内，兼容引擎按关键片段匹配并验证变换，保留宿主与补丁无关的新增内容；片段缺失、匹配歧义、无法验证的历史补丁、版本不符或不安全路径仍停止整批写入。不应为通过检查而补登记未经验证的哈希、删除检查或覆盖成另一设备的程序。这也不承诺兼容任意未来 DSH 版本或任意移植修改。

设置页启用和更新直接调用现有维护事务，仍有执行前复查、互斥、备份与写入校验，只去掉第二次弹窗；关闭与卸载各保留一次确认。自动或手动修复的是磁盘文件，运行中的模块可能尚未更新，仍需按提示重启原 DSH 引擎并刷新网页。

验证应覆盖：宿主无关代码变化的保留；关键片段缺失/重复的整批拒绝；旧补丁升级、幂等及精确还原；启动自动补回和主动关闭标记；正在运行的任务与其他引擎；启用单击执行、关闭可取消和版本/状态变化时禁止 POST。所有修改宿主的集成测试在隔离副本进行，不覆盖正在运行的安装。

## 格式变化兼容

文字上下文匹配失败时，使用 Acorn tokenizer 定位唯一的邻接 token 范围，只替换配方规定的原始字节；不重新打印宿主程序。空格、缩进与不引入换行的注释变化可以保留，token 间的换行约束用于避免自动分号插入差异。关键标识符改变、重复位置、无法精确逆向还原或改动本体已变仍拒绝。字符串中的 TypeScript 声明继续使用专用字段规则，此机制不是任意语义重构适配器。公开多密钥接口仍是长期方向，本次没有更换现有模型路由与配置界面，也没有关闭自动恢复。

## App 更新后分组消失：原因与应对

本次现场为 dsh-go 1.1.0、内置运行时 r15 的新构建，DSH 包版本仍为 0.2.2-rc.1。App 更新替换了五个宿主程序文件；配置中的 9 个密钥分组、38 个模型条目仍存在。当前安装的 0.3.10 仅接受已登记构建，四项新程序被拒绝，且没有启动恢复，因此原生加载器忽略多密钥扩展配置，列表中不再出现这些模型。

beta.1 已允许片段兼容，但请求声明的旧配方要求 apiKey 是最后一项；新宿主在其后增加 headers，仍导致整批拒绝。beta.2 改为解析指定请求的声明字符串、在 apiKey 后加入 keyEntryId 并保留其余声明，同时更新所有匹配的参数校验。这是字段位置兼容修复，没有为这台设备新增哈希白名单。

后续同类更新：插件正常加载后自动识别并补回兼容代码，任务忙时自动等待空闲；已经主动关闭的功能保持关闭。若旧模块已加载，页面只提示重启原引擎并刷新。保留分组配置，不需要删除分组、重建模型或手工登记哈希。如果宿主真正改变必要接口或关键代码结构，插件会报告具体冲突并保留原程序；此时由维护者修复公共兼容逻辑，不能保证任意移植版永远免维护。升级 App 时还应保留插件目录与 profile；插件本身被移除时无法自行运行恢复。

## GitHub 自动检查

向 `main` 提交代码或创建以 `main` 为目标的修改申请后，GitHub 的 **Actions → Automatic checks** 会自动检查：

- 已提交的网页产物是否与源码一致（先检查，再打包，避免打包自动修复后漏报）。
- 仓库现有的自动测试是否通过；完整获取 Git 历史，以运行历史补丁清单验证。
- 能否正常预览生成安装包，以及打包后网页产物是否仍与提交一致。

使用 Node.js 22 和只读仓库权限，不发布 npm、不安装 DSH、不应用补丁。项目使用 Acorn 进行受限的 JavaScript token 上下文定位，依赖由锁文件固定；CI 使用 `npm ci --ignore-scripts` 安装。

检查详情中的红色步骤表示失败，可展开查看原因；绿色表示本次配置的检查通过。没有真实 DSH 程序文件的集成测试会明确跳过，不能视为已经通过。宿主补丁的真实升级、还原和手机窄屏触摸仍按下文单独验证。首次检查流程合并后，也可在 Actions 页点击 **Run workflow** 手动运行。

## 本地验证

需要 Node.js 22 或更新版本。修改网页端源码后，重新生成并提交客户端产物：

```bash
npm run build
npm test
npm run check:build
```

`npm run check:build` 只比对产物，不会覆盖它。历史版本升级测试读取 Git 历史，建议使用完整克隆。部分集成测试需要指定受支持的 DSH 安装目录；未指定时会跳过相应场景。需要覆盖其他已知构建时，可通过 `PI_AI_SOURCES` 传入只包含程序代码的文件，多个路径用系统路径分隔符隔开。集成测试在临时副本中写入，不要提供用户配置或凭据。

```bash
DSH_ROOT=/path/to/dsh npm test
```

## 两类网页代码

- 插件自己的网页界面位于 `src/`，由 `npm run build` 生成 `lib/client.js`。
- DSH 的「设置 → 模型」由宿主提供，发布包中的 `native/*.patch.json` 为已验证的程序文件补丁，不随客户端构建重新生成。生成或修改基准补丁配方时，仍需提供对应的原始程序文件并验证正反变换及完整性；运行时的兼容片段匹配则允许保留基准之外的宿主无关变化。不要直接编辑分发补丁或用其他构建的文件替换。修改生成器后须验证相关构建的启用、升级和还原。

```bash
node scripts/settings-models-collapse.mjs --source /path/to/pristine-client.js
node scripts/settings-models-collapse.mjs --source /path/to/pristine-client.js --check
```

## 触摸排序的验证

设置页密钥分组和模型行共用 `scripts/settings-reorder.mjs` 的指针手势，补丁生成器将其嵌入宿主设置页。长按约 400 毫秒后，以蓝色插入线和「松手后放在这里」提示落点；松手只更新草稿，仍由原表单提交。分组移动时写入每组的 `sortOrder` 数值，模型沿用数组顺序。不能只依赖对象键顺序：宿主配置加载器的相等比较忽略对象键的排列，单纯重排键会被视为未变化。设置和聊天菜单按同一份已保存配置排列，不保存另一份本地排序。

自动测试覆盖长按与防误触、松手坐标、同列表边界、边缘滚动、取消及卸载清理、编辑行身份与输入草稿、只排序的改动提示、失败重试以及选择菜单顺序。发布前仍需在真实手机浏览器核对：短按手柄不移动，手柄以外可滚动；长按拖动折叠/展开分组和模型；长列表边缘滚动；取消后原顺序不变；点击现有保存按钮后，聊天菜单及刷新后的设置顺序一致。模拟事件测试不代表实机触摸已验证。

旧 0.3.8 与 0.3.9-beta.1 的设置补丁，以及 0.3.9-beta.1 的后端补丁，保存在测试夹具中并作为可升级、可还原的历史变体保留。完整程序生成还会验证正向和反向变换均逐字匹配，防止替换片段互相干扰。

## 分组能力批量开关的验证

`src/capability-defaults.js` 的纯函数嵌入设置页。分组可选 `capabilityBatch` 分别记住最近一次识图、思考批量操作，只有已操作的字段才出现。批量操作直接改写当前模型的原生 `input`、`reasoningEfforts`；新增模型应用记住的字段，已有模型单独编辑、改名、重排和重新拉取均不会再次被强制覆盖。后端校验此字段但不拿它覆盖模型能力。原模型行和详情与 0.3.9 保持逐字一致。

旧 beta.1 的 `capabilityDefaults` / `capabilityOverrides` 仍可由后端识别，设置页保存时将有效能力物化为原生字段并删除旧规则。首次打开不自动写配置；保存前后脏状态按物化结果比较。需验证两个批量字段独立、新模型/空 ID/改名、旧规则迁移后单独修改、原生思考关闭不被目录能力重新打开、实际 schema/目录/请求派发、YAML 重读和旧版补丁的精确升级还原。能力与模型列表都由原配置保存接口提交，不另存浏览器规则。实机验收见 `docs/capabilities-beta.md`。

## 诊断与恢复

只读诊断（请替换实际安装路径）：

```bash
node scripts/doctor.mjs --dsh-root /path/to/dsh --json
```

遇到文件校验冲突或无法更新时，先保留现场并收集脱敏诊断。不要强制覆盖程序文件、删除配置或重建密钥。若此前从测试分支安装，可在原 DSH 配置中使用 README 的正式版本命令直接替换插件包，再按更新流程检查补丁。

若插件已误卸载或无法打开网页设置，在处理多密钥模型引用后，先停止正在使用的 DSH 引擎，再从保留的插件目录执行：

```bash
node scripts/native-patches.mjs --dsh-root /path/to/dsh --revert
```

确认恢复完成后，重新启动同一个 DSH 引擎并刷新网页。备份存放在 `DSH_HOME/dsh-model-groups/<安装目录指纹>/backups`。若因异常中断遗留同目录下的 `patch.lock`，请先确认没有补丁维护进程正在运行，切勿并发重试。原版 DSH 可能无法识别 `@dsh-key/` 路由以及 `multiKey`、`keyEntries` 等设置；恢复前请按 README 处理相关模型引用和配置，避免影响启动。
