# 开发与维护指南

日常安装和使用见 [README](../README.md)。

## 0.4.0-alpha.13：可选统一编辑接口

正常客户端只在可选的 `settings.models.provider-editor`、键 `llm-pi-ai` 注册完整编辑器。接口由原生模型页声明并拥有；插件遵守 `open`、`readOnly` 和 `onClose(changed)`，原生页继续拥有账号、供应商卡片及页尾子插槽。生产插件不读取或修改宿主客户端源码。

未提供接口时，不注册第二套 provider-card 表单，也不占用第三方供应商卡片的键位。只在 `settings.models.footer` 的独立 list 项提示限制；分组选择与执行不依赖这个编辑接口。不要把这种降级称为完整统一编辑，也不要为支持它绕过插槽所有权。

`editor-state.js` 使用对象键无序、数组及密钥组顺序有序的语义比较。编辑器管理一个基线和一份草稿；共享名称／连接字段与原单密钥字段只提交真正变化的部分。取消重建基线，折叠保留草稿但关闭发现／移除弹窗；异步发现必须拒绝折叠后到达的旧结果。保存完成时只有仍展开的原编辑器可以调用父级关闭函数，避免关闭已经切换的其他供应商。

`shared.js` 允许 `displayName/api/baseURL/headers`；`single-key.js` 只允许根凭据引用和标准模型字段。按模型 ID 合并未显示的宿主选项，删除用户明确清空的可见字段。原生和插件配置均校验 revision，检查在 journal 和任何配置写入前进行。仅改显示名称不改变路由 token；执行能力或连接变化仍使旧 token 失效。

完整页面隔离验收：

```bash
DSH_EDITOR_CAPABILITY=1 node test/browser/optional-provider-editor.mjs
DSH_EDITOR_CAPABILITY=0 node test/browser/optional-provider-editor.mjs
```

脚本使用原生 Loaded 页面、公开 SlotCore 与真实浏览器；有接口时使用明确标记的宿主内存副本，无接口时使用未修改的原生来源。必须保留第三方卡片／页尾与账号入口，检查统一保存、取消、整组折叠、只读、卸载回退和 390/860 宽度。生成的截图是测试数据，不是已认证本机页面的验收。

接口最小改动只作为可审阅的独立宿主提案与本机试用；安装插件不会自动应用提案，其他移植版无须接受源码补丁才能继续分组和执行。实际试用须保全原文件，并通过宿主正常模块生命周期发布更新后的客户端资源，再刷新现有 GUI；不启动替代服务器，不擅自重启引擎。

## 0.4.0-alpha.12：按 bundle 基准锚定文件

安装行写包内 `./lib/bridge-host-<version>.js`，公共 `parsePatchList` 会以 bundle 补丁文件为基准锚定为 file URL。不能按 profile 再拼 `node_modules`，也不能用 YAML.parse 后手工拼装的行冒充实际安装解析。回归依次执行真实补丁解析、后端导入、ClientModuleRegistry 注册和实际脚本响应。

## 0.4.0-alpha.11：版本化文件入口与前端发现

安装行使用 `./node_modules/dsh-model-groups/lib/bridge-host-<version>.js`，相对 Include 的 profile 基准解析，不含设备绝对路径。ClientModuleRegistry 支持文件入口，会从文件所属 package.json 读取前端声明；唯一版本文件同时避免包根解析缓存继续导入旧后端。真实注册器测试须使用该实际安装行，验证后端导出、启动图、脚本响应及模块 ID 一致。

## 0.4.0-alpha.10：入口改名后的配置重新接入

profile override 的 `name` 是断言；安装行改名后，旧配置可能仍能从可信 Settings 的 `user` 读到，却不在实际 `value` 中。不能把磁盘记录数量当作运行时已启用，也不能直接把 `user` 当作已经提交的配置。

恢复器只处理实际值中缺失的自身记录：验证草稿，并要求当前原生配置完全等于已保存投影（中断日志须符合 before/after），随后经公共 Settings 的 CAS 写入当前入口。不同投影停止，不覆盖外部编辑；恢复冲突不再标记初始化成功。HMR 独占期间受阻时，仍由已认证的原模型页请求重试。

## 0.4.0-alpha.9：前后端共同注册

alpha.9 曾将安装行恢复为包根 `dsh-model-groups`；alpha.11 改为同样可发现、且不复用包根解析缓存的文件入口。当前宿主 ClientModuleRegistry 只识别包根或文件路径，`dsh-model-groups/bridge/<version>` 等子路径可以启动服务端，却不会发布浏览器模块，表现为原模型页多密钥和聊天分组同时消失。

包根的 `exports["."]` 指向按版本构建的完整后端文件，`exports["./client"]` 指向浏览器文件；后端热加载隔离通过文件名实现，不通过安装行子路径实现。回归必须把实际安装行交给真实 ClientModuleRegistry，确认启动图包含插件并能提供与模块 ID 一致的脚本，不能只直接执行客户端 factory。已有显式迁移交接的私密结果可记录 `clientRegistered` 布尔值，用于区分配置激活与前端注册。

## 0.4.0-alpha.8：热加载事务后的初始化

`Settings.mutate` 经过宿主 HMR 独占事务。插件在热加载回调内激活时，微任务和普通定时器会继承该异步事务上下文，延迟执行也不能证明已经离开它。不能访问宿主私有 AsyncLocalStorage 或绕过独占检查。

初始化未完成时，已认证 GET 只返回 `initializationRequired`，保持只读；原模型页随后显式 POST `initialize`，从正常请求上下文重试恢复、导入和投影。POST 仍先验证 owner 身份，多个初始化请求串行合并，页面只在收到提交后的快照后展示完成结果。覆盖启动受阻后重试、访客拒绝和 GET 零写入回归。

## 0.4.0-alpha.5：完整模块图热加载

`scripts/build.mjs` 使用固定开发依赖 esbuild 将插件自身后端编译到按版本区分的 `lib/bridge-host-<version>.js`，公开宿主依赖保持 external。后端文件按版本区分，包根入口通过 exports 选择当前文件，避免仅替换外层入口却复用已缓存的相对导入模块。alpha.5～alpha.8 曾使用子路径安装行；该做法会被前端注册器忽略，已在 alpha.9 改回包根。源码仍在 `src/bridge/host.js`，构建检查同时验证服务端和客户端；`DSH_BRIDGE_ENTRY` 可让真实 host 回归直接执行打包后的入口。

只有已有显式迁移交接时才写入私密结果文件，内容仅含固定阶段、白名单错误码与数量，不含供应商名称、路径、配置、凭据或异常文本。

## 0.4.0-alpha.4：切换旧安装和共用配置

初始化须等待真实 Settings 中出现自身表单，不能在 fiber 激活前读取并把失败当作完成。

`shared.js` 只接受共用 api/baseURL/headers，真实根凭据与未知字段保留在 secret 原配置中；保存和临时发现使用同一草稿。对旧补丁切换，先以私密文件保全原始配置，再通过精确可逆配方撤回旧程序，最后由控制器经公共 Settings CAS 导入；不直接编辑 profile。显式交接文件绑定 Settings documentPath，不覆盖已存在的新记录，原配置发生变化时停止迁移。普通安装不会自行撤回旧源码补丁。

## 0.4.0-alpha.3：原编辑器界面

`legacy-models-ui.js`、`legacy-reorder.js` 与自有前缀的 CSS 静态保留原编辑器结构、模型弹窗、键盘和长按交互；生产运行不读取宿主客户端源码。公开 primitives 由客户端注入，独立渲染才使用语义 fallback。`provider-card.js` 只衔接草稿、凭据、版本检查与生命周期，避免再次设计近似界面。

临时输入的密钥通过独立发现参数传递，只作用于当次模型列表请求；不写入配置、凭据、journal 或运行时缓存。只有“保存”才顺序写入有输入的凭据并提交配置，失败保留未完成输入。测试必须覆盖未完成模型行、模型搜索勾选、能力编辑、单次提交、取消、部分失败与卸载清理。

可选 `test/browser/restore-ui.mjs` 使用真实浏览器分别渲染旧组件基准和当前卡片，在 390/860 宽度、明暗主题下对照表单及模型控件几何，检查弹窗确认和键盘重排，并输出测试数据截图。`DSH_OLD_MODELS_CLIENT` 指定含旧多密钥编辑器的参考客户端；`DSH_UI_TOOLS` 指向独立安装的 React、ReactDOM、esbuild、Playwright 目录。测试基准只在开发脚本中读取，不进入生产依赖。

## 0.4.0-alpha.1：公共服务架构

正常后端入口为 `src/bridge/host.js`，不再加载 `src/index.js` 的旧维护器。旧 `native/`、补丁生成器和精确恢复测试保留用于历史包维护，不属于新版本的正常执行路径。不要为新版本增加移植版配方或自动撤销运行中的旧补丁。

客户端通过 `settings.models.provider-card`、键 `llm-pi-ai` 将编辑区放进原模型页面供应商卡片。`src/client.js` 不注册独立密钥管理页；`providers-form.js` 将已确认投影与插件配置合成只读表单，供模型选择器和备用选择器使用。原表单不能与插件草稿原子提交，使用卡片内单独的“保存”按钮，一次提交凭据与配置。

服务端用公开 Settings 描述/修改接口操作插件命名空间与 `llm-pi-ai` 的供应商配置。整个内部 `bridge` 树标记为 `secret`，普通远程 Settings 描述不能读取 original/journal；可信服务端仍可直接读写并校验 revision。卡片快照只返回必要数据，过滤已知认证头和原始凭据字段；新保存（包括关闭状态）也拒绝这些明文认证字段。控制器先写带 before/after 的 journal，再按原表单 revision 更新原配置，最后提交插件记录；失败、重启或并发编辑时按可观察的前后状态恢复，第三种状态不覆盖。关闭还原原配置；若外部已经编辑则只解除管理。旧开启的 `multiKey/keyEntries` 配置迁移，关闭标记状态不自动启用。

原供应商被投影为只用于公开模型目录与 `prepareCall` 的普通配置，凭据为无上游权限的固定本机占位值、端点为关闭的本机地址。实际请求在公共 `llm/stream` 中间件中交给插件隔离的官方 LLM/适配器运行时：保持公共 provider 身份，模型选择别名解析后使用真实模型 ID、所选密钥引用、端点和协议。原始请求的未知字段、描述符及取消信号尽可能保留；历史回放仅为同一公共模型/密钥重映射，原历史不变。不能将此桥接当成所有私有授权或高级语义都等价。

投影模式通过真实适配器离线解析探测，依次尝试普通模型与旧多密钥模型配置，要求返回的 provider/model 身份精确一致。不是按版本标签、schema 接受未知字段或源码文本猜测能力。无需本地 HTTP 转换代理，不调用收费接口做探测。

`routing.js` 对实际执行配置与解析后的模型能力生成 SHA-256 标识，内部 token 只包含摘要；凭据值不参与摘要，凭据引用参与。根模型与每组模型均使用配置绑定别名。`dispatch.js` 拒绝已失效 token 和受管理的旧裸模型 ID，不把准备于配置 A 的调用交给配置 B；原单密钥通过版本化兼容组重新选择。没有公共 prepare 委托钩子时，这是明确代价。凭据服务自身替换同一引用值遵循宿主的通常凭据语义。

已知契约边界：原生模型配置无法完整投影 `toolUpdate` / `systemPromptUpdate` 等扩展；dsh-go Recall 的私有 WeakMap 授权来源不随描述符复制，内层准备会拒绝受保护辅助调用。测试应验证该请求在凭据/网络前被拒绝，不调用私有继承接口绕过授权。

新架构验证：

```bash
npm ci --ignore-scripts
npm run build
DSH_ROOT=/path/to/current/dsh DSH_PORT_ROOT=/path/to/pristine/public/dsh npm test
npm run check:build
npm pack --dry-run
```

`test/bridge-host.test.mjs` 使用真实 LLM、官方适配器和内存公共 Settings CAS，本地模拟 OpenAI/Anthropic 流式端点验证端到端链路，并比较五个宿主程序哈希未变。目录与传输分别验证；原版及旧补丁适配器都覆盖，不能用旧补丁后的适配器冒充原版能力证明。当前 UI 单元测试不代表已在所有移植版实际网页人工验收。

模块通过宿主公开 Loader 导入，复核应使用真实 profile 的 `baseUrl` 与启动流程中的公共包解析服务（`PluginPackages` / runtime resolution）。只构造裸 Loader 不等于完整启动环境：profile 中通常不直接安装核心包。离线加载回归须覆盖真实 profile 作用域、公共包解析和默认加载路径，不靠写死宿主安装目录或覆盖 `loadModule` 掩盖解析差异。所用 profile 只读，加载和探测不得写入实际配置或发出模型请求。

直接卸载会保留本机目录投影并使请求失败，因此先在原卡片关闭并保存，再切回普通模型，最后卸载。新入口不重启引擎、不改加载器 composition，也不自动卸载历史程序补丁。

以下各节为 0.3.x 历史补丁方案，只有维护旧安装时使用。

## 0.3.12-beta.4：组合宿主重叠改动

DeepCode `kelai141/dsh-mobile-apk` 的 `v0.14.11` 运行包与反馈中的五项程序哈希逐一相同。两个冲突来自语义可组合的上下文变化：模型发现为内置目录增加显式端点限制；设置组件将初始模型改为空行，并在保存时过滤空 ID。旧文本配方把这些宿主内容一起包含在改动锚点中，导致无法匹配。

`discovery-recipes.mjs` 使用 Acorn 找到唯一模型发现函数及直接调用目录的条件块，保留宿主条件原文，并加入插件的所选协议限制。`settings-recipes.mjs` 在唯一设置组件作用域内读取模型状态声明和单密钥过滤链，将其同步保留在候选配方两侧；也处理包含同一声明的后续保存状态配方。两者不按移植版名、版本号或哈希登记兼容，也不重新打印整个宿主函数。精确路径、历史归属、部分补丁、完整逆变换、语法和整批事务检查继续执行。

冲突文件可附带 `matching` 数组，最多 16 项，仅含固定阶段、固定原因码、候选配方下标、原始替换下标及候选数量。下标从 0 开始，展开的组合替换映射回原 manifest 的位置。数组表示尝试路径，不保证每项都是最终唯一原因；不包含源码、动态异常消息、路径或用户配置。

真实移植包通过 `DSH_PORT_ROOT` 提供给 `test/port-runtime.test.mjs`，仅复制五个程序及包元数据到临时目录。测试验证整批应用、重复执行无变化、检查就绪、逐字还原，以及模拟网络下的端点优先、失败不回退目录、所选密钥协议和凭据隔离。`SETTINGS_RECIPES_DSH_ROOT` 可单独验证设置配方；外部完整程序不提交到仓库。

## 0.3.12-beta.3：按代码判定跨版本兼容

安装包不再声明 `engines.dsh` 或 DSH peer dependency 版本范围，保留 Node.js >=22；避免预发布 DSH 版本在读取程序之前被安装器阻断。原始 manifest 的 `version` 继续描述配方来源，不作为宿主或子包的准入值。

维护器识别正确的 DSH 及目标程序包身份，再按实际代码和所需关键结构规划补丁。DSH 版本、子包版本及其预发布或构建标签只记入诊断；版本号不同本身不会停止操作。仍在关键结构缺失、位置歧义、改动冲突或文件/事务条件不满足时停止多密钥维护，不影响独立的分组与折叠。不能把局部变换通过等同于任意版本的完整语义兼容。

公开兼容快照继续使用 `schema: 1` 和可空的 `supportedDsh` 字段以兼容旧客户端；新快照为 `supportedDsh: null`、`compatibilityPolicy: 'code'`，`hostVersion` 与各项 `installedVersion` 均来自实际安装元数据。`host_version` / `package_version` 旧诊断码只用于读取历史报告；当前身份错误使用 `host_identity` / `package_identity`，不会把版本差异误报为冲突。维护协议仍为 2，同协议的网页和后端无需插件版本号完全一致；协议不兼容时才要求刷新网页。

跨版本验收应分别覆盖：只改版本与预发布标签但程序不变、子包独立版本、程序的兼容格式/字段变化，以及关键结构真正不兼容。前几类应能继续计划、应用和还原，后一类应保留现场并指出文件原因；不自动降级，也不添加按版本登记或新的用户确认步骤。

维护票据只绑定维护协议、实际程序及目标配方哈希、操作权限等执行条件，不把版本标签纳入失效条件；只改元数据后刷新仍可沿用票据。已知旧补丁即使缺少当前基准的哈希映射，也会从精确配方确定的原版尝试新版正向变换；不重新猜测代码归属，避免把宿主原生已有的相似代码当成插件代码撤回。升级不适配时仍可按原精确配方还原。

## 按需启用与自动维护偏好

首次安装只提供折叠，不自动计划或写入多密钥补丁。首次手动启用成功后默认打开“自动维护多密钥补丁”；关闭自动维护保留当前补丁，后续宿主覆盖后手动恢复。主动关闭多密钥同时停止自动维护。偏好持久化于插件自己的安装指纹目录，不修改供应商配置或聊天。

已有安装仅依据本插件的旧备份/关闭标记等明确证据迁移，避免把新装用户当成旧用户。启动及空闲重试均先检查偏好；普通状态查询不安装补丁。设置页开关只保存本地偏好，不调用模型 API。

## 0.3.12：维护限制与兼容范围调整

启用、更新及自动恢复只为后续引擎启动准备磁盘补丁，不因当前对话正在生成而禁用。关闭、卸载仍单独检查运行中的任务；使用同一安装目录的其他引擎、文件冲突和并发维护锁仍会阻止写入。启用请求只检查与应用补丁相关的状态变化，卸载权限或回合状态变化不再导致请求失效。修复不会自动重启引擎、刷新网页或宣称已加载新模块；尚未加载的动态模块可能读取新文件，需按重启提示完成切换。

恢复流程等待 timer 服务就绪后启动，避免启动顺序使重试任务未注册；自动补回磁盘代码不依赖可选的 agents 服务。重试异常会结束等待并报告失败；不能确认进程状态与发现其他引擎分别提示。

词法定位依次收集 8、6、4 个 token 的双侧上下文候选，允许较远处无关标识符变化。所有窗口必须指向同一个位置；替换本体、换行约束及精确还原要求保持不变，不重新打印或覆盖宿主其他代码。该机制可扩大文本变化兼容范围，仍不能自动理解任意接口重构。

## 0.3.11-beta.2：启动恢复与片段兼容（历史行为）

0.3.11-beta.2 默认在插件启动时检查并自动补回兼容的多密钥补丁；npm `latest` 仍为 0.3.10，需明确安装此测试版。自动恢复尊重当前安装指纹目录下的 `restore-pending.json`：用户主动关闭后保持关闭，设置页点击 **启用多密钥**可显式恢复。任务运行或其他引擎等限制导致恢复暂缓时，插件在生命周期内每 5 秒检查活动状态，空闲后自动重试；恢复完成、明确关闭或失败后停止。网页在暂缓期间自动刷新状态，显示恢复结果和必要的重启提示。

整文件哈希用于已知版本识别、完整性与事务校验，但不再作为未知构建拒绝的唯一依据。DSH `0.2.2-rc.1` 范围内，兼容引擎按关键片段匹配并验证变换，保留宿主与补丁无关的新增内容；片段缺失、匹配歧义、无法验证的历史补丁、版本不符或不安全路径仍停止整批写入。不应为通过检查而补登记未经验证的哈希、删除检查或覆盖成另一设备的程序。这也不承诺兼容任意未来 DSH 版本或任意移植修改。

设置页启用和更新直接调用现有维护事务，仍有执行前复查、互斥、备份与写入校验，只去掉第二次弹窗；关闭与卸载各保留一次确认。自动或手动修复的是磁盘文件，运行中的模块可能尚未更新，仍需按提示重启原 DSH 引擎并刷新网页。

验证应覆盖：宿主无关代码变化的保留；关键片段缺失/重复的整批拒绝；旧补丁升级、幂等及精确还原；启动自动补回和主动关闭标记；正在运行的任务与其他引擎；启用单击执行、关闭可取消和版本/状态变化时禁止 POST。所有修改宿主的集成测试在隔离副本进行，不覆盖正在运行的安装。

## 格式变化兼容

文字上下文匹配失败时，使用 Acorn tokenizer 定位唯一的邻接 token 范围，只替换配方规定的原始字节；不重新打印宿主程序。空格、缩进与不引入换行的注释变化可以保留，token 间的换行约束用于避免自动分号插入差异。关键标识符改变、重复位置、无法精确逆向还原或改动本体已变仍拒绝。字符串中的 TypeScript 声明继续使用专用字段规则，此机制不是任意语义重构适配器。公开多密钥接口仍是长期方向，本次没有更换现有模型路由与配置界面，也没有关闭自动恢复。

## App 更新后分组消失：原因与应对

本次现场为 dsh-go 1.1.0、内置运行时 r15 的新构建，DSH 包版本仍为 0.2.2-rc.1。App 更新替换了五个宿主程序文件；配置中的 9 个密钥分组、38 个模型条目仍存在。当前安装的 0.3.10 仅接受已登记构建，四项新程序被拒绝，且没有启动恢复，因此原生加载器忽略多密钥扩展配置，列表中不再出现这些模型。

beta.1 已允许片段兼容，但请求声明的旧配方要求 apiKey 是最后一项；新宿主在其后增加 headers，仍导致整批拒绝。beta.2 改为解析指定请求的声明字符串、在 apiKey 后加入 keyEntryId 并保留其余声明，同时更新所有匹配的参数校验。这是字段位置兼容修复，没有为这台设备新增哈希白名单。

后续同类更新：插件正常加载后自动识别并补回兼容代码，任务忙时自动等待空闲；已经主动关闭的功能保持关闭。若旧模块已加载，页面只提示重启原引擎并刷新。保留分组配置，不需要删除分组、重建模型或手工登记哈希。如果宿主真正改变必要接口或关键代码结构，插件会报告具体冲突并保留原程序；此时由维护者修复公共兼容逻辑，不能保证任意移植版永远免维护。升级 App 时还应保留插件目录与 profile；插件本身被移除时无法自行运行恢复。

## GitHub 自动检查

向 `main` 提交代码或创建以 `main` 为目标的修改申请后，GitHub 的 **Actions → Automatic checks** 会自动检查：

- 已提交的网页产物是否与源码一致（先检查，再打包，避免打包自动修复后漏报）。
- 仓库现有的自动测试是否通过；完整获取 Git 历史，以运行历史补丁清单验证。
- 能否正常预览生成安装包，以及打包后网页产物是否仍与提交一致。

使用 Node.js 22 和只读仓库权限，不发布 npm、不安装 DSH、不应用补丁。项目使用 Acorn 进行受限的 JavaScript token 上下文定位，依赖由锁文件固定；CI 使用 `npm ci --ignore-scripts` 安装。

检查详情中的红色步骤表示失败，可展开查看原因；绿色表示本次配置的检查通过。没有真实 DSH 程序文件的集成测试会明确跳过，不能视为已经通过。宿主补丁的真实升级、还原和手机窄屏触摸仍按下文单独验证。首次检查流程合并后，也可在 Actions 页点击 **Run workflow** 手动运行。

## 本地验证

需要 Node.js 22 或更新版本。修改网页端源码后，重新生成并提交客户端产物：

```bash
npm run build
npm test
npm run check:build
```

`npm run check:build` 只比对产物，不会覆盖它。历史版本升级测试读取 Git 历史，建议使用完整克隆。部分集成测试需要指定受支持的 DSH 安装目录；未指定时会跳过相应场景。需要覆盖其他已知构建时，可通过 `PI_AI_SOURCES` 传入只包含程序代码的文件，多个路径用系统路径分隔符隔开。集成测试在临时副本中写入，不要提供用户配置或凭据。

```bash
DSH_ROOT=/path/to/dsh npm test
```

## 两类网页代码

- 插件自己的网页界面位于 `src/`，由 `npm run build` 生成 `lib/client.js`。
- DSH 的「设置 → 模型」由宿主提供，发布包中的 `native/*.patch.json` 为已验证的程序文件补丁，不随客户端构建重新生成。生成或修改基准补丁配方时，仍需提供对应的原始程序文件并验证正反变换及完整性；运行时的兼容片段匹配则允许保留基准之外的宿主无关变化。不要直接编辑分发补丁或用其他构建的文件替换。修改生成器后须验证相关构建的启用、升级和还原。

## 触摸排序的验证

设置页密钥分组和模型行共用 `scripts/settings-reorder.mjs` 的指针手势，补丁生成器将其嵌入宿主设置页。长按约 400 毫秒后，以蓝色插入线和「松手后放在这里」提示落点；松手只更新草稿，仍由原表单提交。分组移动时写入每组的 `sortOrder` 数值，模型沿用数组顺序。不能只依赖对象键顺序：宿主配置加载器的相等比较忽略对象键的排列，单纯重排键会被视为未变化。设置和聊天菜单按同一份已保存配置排列，不保存另一份本地排序。

自动测试覆盖长按与防误触、松手坐标、同列表边界、边缘滚动、取消及卸载清理、编辑行身份与输入草稿、只排序的改动提示、失败重试以及选择菜单顺序。发布前仍需在真实手机浏览器核对：短按手柄不移动，手柄以外可滚动；长按拖动折叠/展开分组和模型；长列表边缘滚动；取消后原顺序不变；点击现有保存按钮后，聊天菜单及刷新后的设置顺序一致。模拟事件测试不代表实机触摸已验证。

旧 0.3.8 与 0.3.9-beta.1 的设置补丁，以及 0.3.9-beta.1 的后端补丁，保存在测试夹具中并作为可升级、可还原的历史变体保留。完整程序生成还会验证正向和反向变换均逐字匹配，防止替换片段互相干扰。

## 分组能力批量开关的验证

`src/capability-defaults.js` 的纯函数嵌入设置页。分组可选 `capabilityBatch` 分别记住最近一次识图、思考批量操作，只有已操作的字段才出现。批量操作直接改写当前模型的原生 `input`、`reasoningEfforts`；新增模型应用记住的字段，已有模型单独编辑、改名、重排和重新拉取均不会再次被强制覆盖。后端校验此字段但不拿它覆盖模型能力。原模型行和详情与 0.3.9 保持逐字一致。

旧 beta.1 的 `capabilityDefaults` / `capabilityOverrides` 仍可由后端识别，设置页保存时将有效能力物化为原生字段并删除旧规则。首次打开不自动写配置；保存前后脏状态按物化结果比较。需验证两个批量字段独立、新模型/空 ID/改名、旧规则迁移后单独修改、原生思考关闭不被目录能力重新打开、实际 schema/目录/请求派发、YAML 重读和旧版补丁的精确升级还原。能力与模型列表都由原配置保存接口提交，不另存浏览器规则。实机验收见 `docs/capabilities-beta.md`。

## 诊断与恢复

只读诊断（请替换实际安装路径）：

```bash
node scripts/doctor.mjs --dsh-root /path/to/dsh --json
```

遇到文件校验冲突或无法更新时，先保留现场并收集脱敏诊断。不要强制覆盖程序文件、删除配置或重建密钥。若此前从测试分支安装，可在原 DSH 配置中使用 README 的正式版本命令直接替换插件包，再按更新流程检查补丁。

若插件已误卸载或无法打开网页设置，在处理多密钥模型引用后，先停止正在使用的 DSH 引擎，再从保留的插件目录执行：

```bash
node scripts/native-patches.mjs --dsh-root /path/to/dsh --revert
```

确认恢复完成后，重新启动同一个 DSH 引擎并刷新网页。备份存放在 `DSH_HOME/dsh-model-groups/<安装目录指纹>/backups`。若因异常中断遗留同目录下的 `patch.lock`，请先确认没有补丁维护进程正在运行，切勿并发重试。原版 DSH 可能无法识别 `@dsh-key/` 路由以及 `multiKey`、`keyEntries` 等设置；恢复前请按 README 处理相关模型引用和配置，避免影响启动。
